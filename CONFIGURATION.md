# Configuration Guide v2.0

Полное руководство по конфигурации Data Exporter Service версии 2.0.

## 📋 Обзор

Data Exporter Service использует TOML формат конфигурации. Файл конфигурации находится по адресу:
```
C:\Program Files\data-exporter\config.toml
```

### Минимальная конфигурация

```toml
version = "2.0"

[auth]
domain = "store-01.example.com"
client_secret = "a1b2c3d4-e5f6-7890-abcd-ef1234567890"

[api]
base_url = "https://middleware.example.com"

[source]
directory = "C:\\Data\\DBF"

[schedule]
crontab = "0 8,12,16,18 * * *"
```

### Полная конфигурация

```toml
version = "2.0"

[auth]
domain = "store-01.example.com"
client_secret = "a1b2c3d4-e5f6-7890-abcd-ef1234567890"

[api]
base_url = "https://middleware.example.com"

[source]
directory = "C:\\Data\\DBF"

[schedule]
crontab = "0 8,12,16,18 * * *"

[encoding]
dbf_encoding = "CP866"

[batch]
max_files_per_batch = 100
chunk_size_mb = 10
max_retries = 3
retry_delay_seconds = 30

[logging]
level = "info"
error_log_path = "error.log"
```

## 🔧 Секции конфигурации

### version

**Обязательность**: Обязательно
**Тип**: String
**Значения**: `"2.0"`

Версия формата конфигурации. Обязательно должна быть `"2.0"` для версии 2.x.

```toml
version = "2.0"
```

### [auth] - Аутентификация

Настройки аутентификации через site credentials.

#### domain

**Обязательность**: Обязательно
**Тип**: String
**Формат**: Полный домен сайта
**Пример**: `"store-01.example.com"`

Домен вашего сайта для аутентификации в middleware. Используется как часть site credentials вместе с client_secret.

**Получение**:
1. Войдите в панель управления middleware
2. Скопируйте domain вашего сайта

**Валидация**:
- Не может быть пустым
- Должен быть валидным доменным именем
- Без протокола (`http://` или `https://`)

```toml
[auth]
domain = "store-01.example.com"
```

**Примеры валидных доменов**:
- `store-01.example.com`
- `shop.company.com`
- `data-export-site.example.org`

**Примеры невалидных доменов**:
- `https://store-01.example.com` ❌ (содержит протокол)
- `store-01` ❌ (неполный домен)
- ` ` ❌ (пустая строка)

#### client_secret

**Обязательность**: Обязательно
**Тип**: String
**Формат**: UUID (xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx)
**Пример**: `"a1b2c3d4-e5f6-7890-abcd-ef1234567890"`

Секретный ключ для аутентификации. Используется вместе с domain для получения JWT токена.

**Получение**:
1. Войдите в панель управления middleware
2. Перейдите в раздел "API Credentials"
3. Сгенерируйте новый client_secret
4. Скопируйте значение (показывается только один раз!)

**Безопасность**:
- ⚠️ Никогда не сохраняйте в системе контроля версий
- ⚠️ Не передавайте в логах или ошибках
- ⚠️ Храните в безопасном месте (config.toml доступен только администраторам)
- ✅ Периодически обновляйте (рекомендуется раз в 90 дней)

```toml
[auth]
client_secret = "a1b2c3d4-e5f6-7890-abcd-ef1234567890"
```

**Валидация**:
- Формат UUID (8-4-4-4-12 символов)
- Не может быть пустым

### [api] - API подключение

Настройки подключения к middleware API.

#### base_url

**Обязательность**: Обязательно
**Тип**: String
**Формат**: HTTPS URL
**Пример**: `"https://middleware.example.com"`

Базовый URL middleware API. Используется для всех API запросов (аутентификация, batch operations, error reporting).

**Требования**:
- ✅ Обязательно HTTPS (HTTP разрешён только для localhost тестирования)
- ✅ Без trailing slash (`/` в конце)
- ✅ Доступен из сети Windows сервера

```toml
[api]
base_url = "https://middleware.example.com"
```

**Примеры валидных URL**:
- `https://middleware.example.com`
- `https://api.company.com`
- `http://localhost:3000` (только для тестирования)
- `http://127.0.0.1:3000` (только для тестирования)

**Примеры невалидных URL**:
- `http://middleware.example.com` ❌ (HTTP в production)
- `https://middleware.example.com/` ❌ (trailing slash)
- `middleware.example.com` ❌ (без протокола)

**Используемые endpoints**:
- `POST /api/v1/auth/token` - Получение JWT токена
- `POST /api/v1/batch/start` - Начало batch загрузки
- `POST /api/v1/batch/{batchId}/upload` - Загрузка файлов
- `POST /api/v1/batch/{batchId}/complete` - Завершение batch
- `POST /api/v1/batch/{batchId}/fail` - Сообщение об ошибке batch
- `POST /api/v1/batch/{batchId}/cancel` - Отмена batch
- `POST /api/v1/error` - Отправка standalone ошибок
- `POST /api/v1/error/{batchId}` - Отправка batch ошибок

### [source] - Исходные данные

Настройки папки с исходными DBF файлами.

#### directory

**Обязательность**: Обязательно
**Тип**: String (Windows path)
**Формат**: Абсолютный путь с двойными обратными слешами
**Пример**: `"C:\\Data\\DBF"`

Путь к папке с DBF файлами для обработки.

**Требования**:
- ✅ Абсолютный путь (не относительный)
- ✅ Двойные обратные слеши (`\\`) в TOML формате
- ✅ Папка должна существовать
- ✅ Windows сервис должен иметь права на чтение

```toml
[source]
directory = "C:\\Data\\DBF"
```

**Примеры валидных путей**:
- `"C:\\Data\\DBF"`
- `"D:\\Export\\Files"`
- `"\\\\server\\share\\DBF"`

**Примеры невалидных путей**:
- `C:\Data\DBF` ❌ (одинарные слеши в TOML)
- `Data\DBF` ❌ (относительный путь)
- `/data/dbf` ❌ (Unix формат)

**Поведение сканирования**:
- Сканируются только файлы с расширением `.dbf` (регистронезависимо)
- Поддиректории не сканируются (только корневая папка)
- Заблокированные файлы пропускаются с логированием
- Обработанные файлы не удаляются (обрабатываются повторно при следующем запуске)

### [schedule] - Расписание

Настройки расписания автоматического запуска.

#### crontab

**Обязательность**: Обязательно
**Тип**: String (cron expression)
**Формат**: Cron (5 полей)
**Пример**: `"0 8,12,16,18 * * *"`

Расписание выполнения обработки в формате cron.

**Формат cron**:
```
 ┌──── минута (0-59)
 │ ┌─── час (0-23)
 │ │ ┌─ день месяца (1-31)
 │ │ │ ┌ месяц (1-12)
 │ │ │ │ ┌ день недели (0-6, 0=воскресенье)
 │ │ │ │ │
 * * * * *
```

```toml
[schedule]
crontab = "0 8,12,16,18 * * *"
```

**Примеры расписаний**:

| Расписание | Описание |
|------------|----------|
| `*/5 * * * *` | Каждые 5 минут |
| `0 * * * *` | Каждый час (в начале часа) |
| `0 */2 * * *` | Каждые 2 часа |
| `0 9 * * *` | Ежедневно в 9:00 |
| `0 9 * * 1-5` | В 9:00 по будням (понедельник-пятница) |
| `0 8,12,16,18 * * *` | В 8:00, 12:00, 16:00, 18:00 каждый день |
| `30 2 * * 0` | В 2:30 каждое воскресенье |
| `0 0 1 * *` | В полночь 1-го числа каждого месяца |

**Рекомендации**:
- 🎯 Настраивайте исходя из частоты обновления DBF файлов
- ⚡ Избегайте слишком частых запусков (< 5 минут) без необходимости
- 🌙 Рассмотрите запуск в нерабочее время для больших объёмов
- 📊 Учитывайте время обработки (следующий запуск не начнётся пока текущий не завершён)

### [encoding] - Кодировки

Настройки обработки кодировок DBF файлов.

#### dbf_encoding

**Обязательность**: Опционально
**Тип**: String
**Значение по умолчанию**: `"CP866"`
**Возможные значения**: `"CP866"`, `"Windows-1251"`, `"UTF-8"`

Fallback кодировка для DBF файлов, которые не содержат информацию о кодировке в заголовке.

```toml
[encoding]
dbf_encoding = "CP866"
```

**Приоритет определения кодировки**:
1. **Автоопределение** - если DBF файл содержит language driver ID в заголовке
2. **Fallback** - используется `dbf_encoding` из конфигурации

**Выбор кодировки**:

| Кодировка | Когда использовать |
|-----------|-------------------|
| `CP866` (default) | DOS кодировка, старые DBF файлы |
| `Windows-1251` | Windows кириллица, современные DBF |
| `UTF-8` | Современные системы, Unicode |

**Симптомы неправильной кодировки**:
- Кракозябры в русском тексте
- Замена кириллицы на `?` или `�`
- Неправильное отображение специальных символов

**Решение**:
1. Определите кодировку исходных DBF файлов
2. Установите соответствующую fallback кодировку
3. Проверьте корректность конвертации в CSV

### [batch] - Batch загрузка

Настройки batch protocol и обработки групп файлов.

#### max_files_per_batch

**Обязательность**: Опционально
**Тип**: Unsigned Integer
**Значение по умолчанию**: `100`
**Диапазон**: `1` - `1000`

Максимальное количество файлов в одной batch группе.

```toml
[batch]
max_files_per_batch = 100
```

**Влияние на производительность**:
- **Маленькие значения (1-50)**:
  - ✅ Меньше ресурсов памяти
  - ✅ Быстрее завершение каждого batch
  - ❌ Больше overhead на создание batch

- **Большие значения (100-1000)**:
  - ✅ Меньше overhead
  - ✅ Эффективнее для большого количества файлов
  - ❌ Больше памяти
  - ❌ Дольше выполнение одного batch

**Рекомендации**:
- 50-100: Оптимально для большинства случаев
- 10-50: Если ограничены ресурсы памяти
- 200-500: Для обработки большого количества мелких файлов

#### chunk_size_mb

**Обязательность**: Опционально
**Тип**: Unsigned Integer
**Значение по умолчанию**: `10`
**Диапазон**: `1` - `100` МБ

Размер chunk для загрузки больших файлов (в мегабайтах).

```toml
[batch]
chunk_size_mb = 10
```

**Поведение**:
- Файлы меньше `chunk_size_mb` загружаются целиком
- Файлы больше `chunk_size_mb` разбиваются на части и загружаются по частям

**Влияние на производительность**:
- **Маленькие chunks (1-5 МБ)**:
  - ✅ Меньше памяти на загрузку
  - ✅ Лучше для медленных соединений
  - ❌ Больше HTTP запросов

- **Большие chunks (20-100 МБ)**:
  - ✅ Меньше HTTP запросов
  - ✅ Быстрее для больших файлов
  - ❌ Больше памяти
  - ❌ Риск timeout на медленных соединениях

**Рекомендации**:
- 5-10 МБ: Оптимально для большинства случаев
- 1-5 МБ: Медленное или нестабильное соединение
- 20-50 МБ: Быстрое соединение и большие файлы

#### max_retries

**Обязательность**: Опционально
**Тип**: Unsigned Integer
**Значение по умолчанию**: `3`
**Диапазон**: `0` - `10`

Количество попыток повтора при временных ошибках загрузки.

```toml
[batch]
max_retries = 3
```

**Поведение retry**:
- Повторы выполняются только для временных ошибок (503, network timeout)
- Постоянные ошибки (401, 400) не повторяются
- Используется экспоненциальная задержка между попытками

**Примеры**:
- `0` - нет повторов (fail immediately)
- `3` - до 3 дополнительных попыток (4 попытки всего)
- `5` - до 5 дополнительных попыток (6 попыток всего)

**Рекомендации**:
- 3: Стабильная сеть
- 5: Нестабильная сеть или middleware
- 0: Только для тестирования

#### retry_delay_seconds

**Обязательность**: Опционально
**Тип**: Unsigned Integer
**Значение по умолчанию**: `30`
**Диапазон**: `1` - `300` секунд

Начальная задержка между повторами (в секундах).

```toml
[batch]
retry_delay_seconds = 30
```

**Поведение**:
- Используется экспоненциальная задержка: `delay * 2^attempt`
- Пример с `retry_delay_seconds = 30`:
  - 1-я попытка: сразу
  - 2-я попытка: через 30 сек
  - 3-я попытка: через 60 сек (30 * 2)
  - 4-я попытка: через 120 сек (30 * 4)

**Рекомендации**:
- 10-30 сек: Быстрые повторы для временных сбоев
- 60-120 сек: Медленные повторы для стабильности
- 5 сек: Только для тестирования

### [logging] - Логирование

Настройки логирования и отчётов об ошибках.

#### level

**Обязательность**: Опционально
**Тип**: String
**Значение по умолчанию**: `"info"`
**Возможные значения**: `"trace"`, `"debug"`, `"info"`, `"warn"`, `"error"`

Уровень детализации логов в Windows Event Log.

```toml
[logging]
level = "info"
```

**Уровни логирования**:

| Уровень | Что логируется | Когда использовать |
|---------|----------------|-------------------|
| `trace` | Всё включая детали внутренних операций | Детальная отладка |
| `debug` | Отладочная информация, входы/выходы функций | Разработка, troubleshooting |
| `info` | Основные события (start, complete, errors) | Production (default) |
| `warn` | Предупреждения и потенциальные проблемы | Production |
| `error` | Только ошибки | Минимальное логирование |

**Рекомендации**:
- `info`: Оптимально для production
- `debug`: Временно для диагностики проблем
- `warn` или `error`: Минимизация логов в стабильной среде
- `trace`: Только для разработки (очень много логов!)

**Просмотр логов**:
```powershell
# Event Viewer
eventvwr.msc
# Windows Logs → Application → Source: "data-exporter"
```

#### error_log_path

**Обязательность**: Опционально
**Тип**: String (file path)
**Значение по умолчанию**: `"error.log"`
**Формат**: Относительный или абсолютный путь

Путь к файлу для fallback логирования ошибок (когда middleware API недоступен).

```toml
[logging]
error_log_path = "error.log"
```

**Поведение fallback**:
1. Сервис пытается отправить ошибку на middleware API
2. Если API недоступен → ошибка записывается в `error_log_path`
3. Локальный лог гарантирует, что ошибки не теряются

**Примеры путей**:
- `"error.log"` - относительный путь (рядом с exe)
- `"logs\\error.log"` - поддиректория logs
- `"C:\\Logs\\data-exporter-errors.log"` - абсолютный путь

**Формат записей**:
```
[2025-10-05T14:30:00Z] UploadError - Network timeout
[2025-10-05T14:35:12Z] BatchError - Failed to complete batch abc-123
```

**Обслуживание**:
- Файл растёт со временем
- Рекомендуется периодическая ротация (вручную или через скрипт)
- Проверяйте размер файла регулярно

## 🔍 Валидация конфигурации

Сервис проверяет конфигурацию при запуске:

### Проверки при запуске

1. **Синтаксис TOML** - валидный TOML формат
2. **Обязательные поля** - version, auth.*, api.*, source.*, schedule.*
3. **Валидация значений**:
   - `version` = "2.0"
   - `auth.domain` - не пустой, валидный домен
   - `auth.client_secret` - не пустой, UUID формат
   - `api.base_url` - HTTPS URL (или HTTP localhost)
   - `source.directory` - существующая папка
   - `schedule.crontab` - валидный cron expression

### Ошибки валидации

При ошибках валидации сервис:
1. Логирует ошибку в Event Viewer
2. Не запускается до исправления конфигурации

**Пример ошибки**:
```
[ERROR] Configuration validation failed: Invalid auth.client_secret format (expected UUID)
```

**Решение**:
1. Откройте `config.toml`
2. Исправьте указанное поле
3. Перезапустите сервис

## 🔄 Hot Reload

Конфигурация поддерживает "горячую" перезагрузку:

### Как работает Hot Reload

1. Сервис отслеживает изменения `config.toml`
2. При изменении файла - перезагружает конфигурацию
3. Новая конфигурация применяется при следующем запланированном запуске
4. Текущая обработка **не прерывается**

### Процедура обновления

```powershell
# 1. Отредактируйте config.toml
notepad "C:\Program Files\data-exporter\config.toml"

# 2. Сохраните изменения
# (автоматически обнаружатся сервисом)

# 3. Изменения применятся при следующем запуске по расписанию
```

### Ограничения Hot Reload

Изменения применяются **только между запусками**:
- ✅ Новый `crontab` - применится сразу после текущего выполнения
- ✅ Новые `batch` настройки - применятся при следующем batch
- ✅ Новый `logging.level` - применится при следующем запуске
- ❌ Изменения **не применяются** во время активной обработки

**Пример**:
```
12:00 - Начало обработки (используется старая конфигурация)
12:05 - Изменение config.toml
12:10 - Обработка завершена
12:15 - Следующая обработка (используется НОВАЯ конфигурация)
```

## 🐛 Troubleshooting

### Сервис не стартует

**Симптомы**: Service status = "Stopped", ошибки в Event Viewer

**Проверки**:
```powershell
# Проверьте синтаксис TOML
Get-Content "C:\Program Files\data-exporter\config.toml"

# Проверьте логи
eventvwr.msc
# Windows Logs → Application → Source: "data-exporter"
```

**Частые ошибки**:
1. Неправильный формат TOML (пропущена кавычка, скобка)
2. Отсутствует обязательное поле
3. Неверный формат пути (одинарные слеши)
4. Несуществующая папка source.directory

### Файлы не обрабатываются

**Симптомы**: Сервис работает, но файлы не загружаются

**Проверки**:
```powershell
# Проверьте source directory
Test-Path "C:\Data\DBF"
Get-ChildItem "C:\Data\DBF\*.dbf"

# Проверьте расписание
# Убедитесь, что текущее время соответствует crontab

# Проверьте логи
Get-Content "C:\Program Files\data-exporter\error.log"
```

**Частые причины**:
1. Неправильный путь source.directory
2. Нет прав на чтение папки
3. Нет DBF файлов в папке
4. Расписание не соответствует текущему времени
5. Middleware API недоступен

### Ошибки аутентификации

**Симптомы**: "Authentication failed" в логах

**Решение**:
```toml
# Проверьте credentials в middleware панели
[auth]
domain = "correct-domain.example.com"
client_secret = "correct-uuid-from-panel"

# Проверьте HTTPS
[api]
base_url = "https://middleware.example.com"  # Не http://
```
