# API Contract: File Upload

**Endpoint**: `POST /api/files/upload`
**Purpose**: Upload compressed CSV file (gzip format) to server
**Used By**: File Uploader (during batch processing)

## Request

### Method
`POST`

### Headers
```
Authorization: Bearer <jwt_token>
Content-Type: multipart/form-data; boundary=<boundary>
Content-Encoding: gzip
```

**Header Descriptions**:
- `Authorization`: JWT token obtained from `/api/auth/token`
  - Format: `Bearer <token>`
- `Content-Type`: Multipart form data with boundary
  - Auto-generated by HTTP client (reqwest)
- `Content-Encoding`: Indicates gzip compression
  - Value: `gzip`

### Request Body (Multipart Form Data)

**Form Fields**:
- `file`: Binary file data (gzip-compressed CSV)
  - Field name: `file`
  - Filename: Generated from DBF relative path (e.g., `subdir_data.csv.gz`)
  - Content-Type: `application/gzip` or `application/octet-stream`

**Multipart Structure**:
```
--boundary
Content-Disposition: form-data; name="file"; filename="subdir_data.csv.gz"
Content-Type: application/gzip

<binary gzip data>
--boundary--
```

## Response

### Success Response (200 OK or 201 Created)

#### Headers
```
Content-Type: application/json
```

#### Body Schema
```json
{
  "status": "string",
  "message": "string",
  "file_id": "string (optional)"
}
```

#### Field Descriptions
- `status`: Success indicator
  - Value: `"success"` or `"uploaded"`
- `message`: Human-readable confirmation
  - Example: `"File uploaded successfully"`
- `file_id`: Server-assigned identifier (optional)
  - Used for server-side tracking and versioning

#### Example Success Response
```json
{
  "status": "success",
  "message": "File uploaded successfully",
  "file_id": "abc-123-xyz"
}
```

### Error Responses

#### 401 Unauthorized - Invalid or Expired Token
```json
{
  "error": "unauthorized",
  "message": "Invalid or expired token"
}
```

**When**: JWT token missing, invalid, or expired
**Client Action**: Request new token, retry upload

#### 400 Bad Request - Missing File or Invalid Format
```json
{
  "error": "bad_request",
  "message": "File is required"
}
```

**OR**

```json
{
  "error": "bad_request",
  "message": "Invalid file format"
}
```

**When**: File field missing or file not gzip-compressed
**Client Action**: Log error, report to error endpoint, skip file

#### 413 Payload Too Large
```json
{
  "error": "payload_too_large",
  "message": "File size exceeds maximum allowed"
}
```

**When**: File exceeds server size limit
**Client Action**: Log error, report to error endpoint, skip file

#### 422 Unprocessable Entity - Server Rejects File
```json
{
  "error": "unprocessable_entity",
  "message": "File validation failed: Invalid CSV structure"
}
```

**When**: Server-side validation fails (e.g., quota exceeded, invalid content)
**Client Action**: Log error, report to error endpoint, delete local CSV, skip file

#### 500 Internal Server Error
```json
{
  "error": "internal_error",
  "message": "An internal error occurred"
}
```

**When**: Server-side processing error
**Client Action**: Log error, report to error endpoint, retry with exponential backoff (max 3 attempts)

#### 503 Service Unavailable
```json
{
  "error": "service_unavailable",
  "message": "Service temporarily unavailable"
}
```

**When**: Server overloaded or under maintenance
**Client Action**: Write to local error log, skip current batch

## Client Behavior Requirements

### Pre-Upload Checks
1. Verify JWT token is present and not expired
2. Verify gzip file exists and is readable
3. Generate correct filename from DBF relative path

### On Success (200/201)
1. Log successful upload
2. Delete local CSV file (cleanup)
3. Continue with next file in batch

### On 401 Unauthorized
1. Request new JWT token
2. Retry upload with new token (once)
3. If retry fails: Report error, skip file

### On 4xx Client Errors (400, 413, 422)
1. Log error details
2. Send error report to `/api/errors/report`
3. Delete local CSV file (per clarification: delete regardless of upload success/failure)
4. Continue with next file (do not retry)

### On 5xx Server Errors (500, 503)
1. Retry with exponential backoff (delays: 1s, 2s, 4s)
2. Maximum 3 retry attempts
3. If all retries fail:
   - Write error to local error log (fallback)
   - Delete local CSV file
   - Continue with next file

### On Network Error
1. Write error to local error log
2. Delete local CSV file
3. Continue with next file (file will be re-processed on next scheduled run)

## File Naming Convention

**Source**: `C:\Program Files\abc\def\subdir1\subdir2\data.dbf`
**Relative Path**: `subdir1\subdir2\data.dbf`
**Compressed Filename**: `subdir1_subdir2_data.csv.gz`

**Transformation Rules**:
1. Extract relative path from source_dir
2. Replace path separators (`\`) with underscores (`_`)
3. Replace `.dbf` extension with `.csv.gz`

**Example Transformations**:
- `data.dbf` → `data.csv.gz`
- `reports\monthly.dbf` → `reports_monthly.csv.gz`
- `archive\2024\january\sales.dbf` → `archive_2024_january_sales.csv.gz`

## Security Requirements

- **HTTPS Only**: All uploads must use HTTPS (TLS/SSL)
- **Authentication**: JWT Bearer token required in Authorization header
- **Token Validation**: Server must validate token signature and expiration
- **Content Validation**: Server may validate gzip format and CSV structure

## Contract Tests

The following test scenarios must be implemented:

1. **Successful Upload**
   - Given: Valid JWT token and valid gzip file
   - When: POST to /api/files/upload
   - Then: Receive 200/201 with success status

2. **Missing Authorization**
   - Given: No Authorization header
   - When: POST to /api/files/upload
   - Then: Receive 401 Unauthorized

3. **Expired Token**
   - Given: Expired JWT token
   - When: POST to /api/files/upload
   - Then: Receive 401 Unauthorized

4. **Missing File**
   - Given: Multipart request without file field
   - When: POST to /api/files/upload
   - Then: Receive 400 Bad Request

5. **Invalid File Format**
   - Given: Non-gzip file uploaded
   - When: POST to /api/files/upload
   - Then: Receive 400 or 422 error

6. **Large File Upload**
   - Given: File exceeds server size limit
   - When: POST to /api/files/upload
   - Then: Receive 413 Payload Too Large

7. **Filename Encoding**
   - Given: DBF file in subdirectory (e.g., `sub\data.dbf`)
   - When: Generate filename and upload
   - Then: Filename is `sub_data.csv.gz`

8. **HTTPS Enforcement**
   - Given: HTTP URL (not HTTPS)
   - When: Attempt upload
   - Then: Client rejects request

9. **Duplicate Filename**
   - Given: Multiple uploads with same filename
   - When: POST to /api/files/upload
   - Then: Server handles versioning (client doesn't track duplicates)

## Notes

- Server is responsible for file versioning and deduplication
- Client does not track previously uploaded files
- Client always deletes local CSV after upload attempt (success or failure)
- Gzip decompression and CSV validation are server-side responsibilities
- Network failures result in file being re-processed on next scheduled run (idempotency)
